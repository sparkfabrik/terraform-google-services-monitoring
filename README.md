# Terraform GCP Services Monitoring Module

This module creates a set of monitoring alerts for Google Cloud Platform services.

Supported services:

- Cloud SQL
  - CPU usage
  - Storage usage
  - Memory usage

- Memorystore
  - CPU utilization alerts for Redis instances and Redis clusters
  - Memory (system memory usage ratio) alerts for Redis instances and Redis clusters

- Kyverno
  - Error logs for admission-controller, background-controller, cleanup-controller, reports-controller

- cert-manager
  - Error logs for cert-manager controller when an Issuer or ClusterIssuer is missing

- Konnectivity agent
  - Alert when no pods are available for the konnectivity-agent deployment

- SSL certificate expiration
  - SSL certificate expiry alerts for monitored endpoints

- Typesense
  - Uptime checks for HTTP endpoints
  - Pod restart alerts for Typesense containers

- LiteLLM
  - Uptime checks for HTTP endpoints
  - Pod restart alerts for LiteLLM containers

- Vertex AI
  - Consumption dashboard: a note stating that the cost is an upper bound and when the price table was last checked, estimated cost per model, tokens by model and by type, consumed token throughput, invocations per second per model, invocations by response code and by error category, invocation latency p50 and p95, first-token latency
  - Estimated-cost alerts on one or more named thresholds, each with its own window and notification channels
  - Invocation error-rate alert on the share of a given response code, 429 by default, evaluated per model and only above a minimum invocation count

### Vertex AI: the cost figure is an upper bound

**Read this before enabling the service.**

Vertex AI publishes token counts to Cloud Monitoring but **no spend metric**, so this module cannot read your cost from Google. It estimates it: tokens multiplied by the published list price, in USD.

That estimate reads high, and by a margin worth knowing before you set a threshold on it. Google bills a prompt token it served from its **implicit context cache** at a tenth of the input price, under a SKU of its own. The metric does not make that distinction: for Google's own models the `type` label only ever takes the values `input` and `output`, so cache reads sit inside `input` and the estimate charges them at the full rate.

Implicit caching is on by default on recent Gemini models. On a production workload reconciled against its invoice, cache reads were about a third of the prompt tokens and the estimate landed roughly 40% above the billed input cost.

Nothing in Cloud Monitoring exposes the split, so the module does not try to correct it:

- The `explicit_caching` label on the metric is populated only for partner models, and it marks the request rather than separating the tokens inside it.
- No metric in any namespace carries a cached-token count. A scan of every metric descriptor in a live project found none.
- The cache token types the module does price (`cache_read_input` and the `cache_write` ones) exist only on partner-model series. **Adding such an entry to a Gemini model produces a PromQL term that matches nothing and silently costs zero** — that is not the way to fix the overestimate.

What you get instead is a guarantee of direction: the figure is never below the list-price cost of the traffic it counts, so a threshold set on it fires early and never late. For the amount actually billed, and for the cached share as a line of its own, use the BigQuery billing export.

### Vertex AI: keeping the price table current

The price table ships as a module default in `vertex_ai.pricing` and **must be reviewed periodically**. Nothing updates it and nothing reports it wrong: a stale price produces a confident wrong number with no error and no visible symptom.

It is, however, verifiable. Every value in it is a list price published in the **Cloud Billing Catalog**, which is public and needs no billing permission:

```bash
TOKEN=$(gcloud auth print-access-token)
curl -s -H "Authorization: Bearer $TOKEN" \
  "https://cloudbilling.googleapis.com/v1/services/C7E2-9256-1C43/skus?pageSize=5000" \
| jq -r '.skus[] | select(.description | test("Gemini 3.5 Flash Global Text"))
         | "\(.description)\t\(.pricingInfo[-1].pricingExpression.tieredRates[-1].unitPrice.nanos/1000) USD/1M"'
```

Swap the `test()` pattern for the model you are checking. The service to query depends on the vendor, which is the easy mistake:

| Service id | Covers |
| --- | --- |
| `C7E2-9256-1C43` | Vertex AI — Gemini and the embedding models |
| `EC6A-CCB9-60E9` | Claude Sonnet 4.6 |
| `BD63-1A21-A8FA` | Claude Sonnet 5 |

Partner models are **not** under the Vertex AI service: searching its 8.8k SKUs for `claude` returns nothing, which reads like "no SKU exists" and is how this table was once documented. Read only the `- Predictions` rows: the same model also publishes Off-Peak and Flex rows at half price and Priority rows at 1.8x, and this table prices the standard tier, which is what the metric reports as `request_type="shared"` and `shared_request_type="standard"`.

Four ways the table goes stale, all seen in practice:

- **A price changes.** One shipped entry carried an introductory rate with a note saying it expired on 2026-12-31; the catalog had already moved to the standard price, so the table understated that model by 50% before the date in its own comment. Check against the catalog, not against the comment.
- **A discount hides the drift.** A promotional rate lands on the invoice as a credit in the "Other savings" column, not as a lower list price. The table prices at list, so the estimate does not see it and the invoice is lower than the estimate for a second, unrelated reason.
- **A new model appears.** A model routed through your gateway shows up in the token widgets immediately and contributes nothing to the cost, because it has no price. Comparing "Tokens by model" against "Estimated cost by model" is how you spot it — with the caveat that batch traffic is excluded from the cost side only, so a model serving batch alone also shows this way.
- **Your own table drifts from the module's.** If you override `pricing`, you own it entirely, including `pricing_verified_on`, the date the dashboard shows.

Put the review on a recurring issue, and re-inventory the live `token_count` series each time so models that appeared in the meantime are caught rather than assumed absent.

### Reading the Vertex AI dashboard

The first tile states that the figures are an upper bound and when the table was last checked. Beyond the caching caveat above, list prices also ignore committed-use discounts, negotiated rates and credits, and **batch traffic is left out of the cost entirely** — the metric reports it with a `batch_` prefix on its `source` label and it is billed at a different rate, so it is excluded rather than mispriced. A batch job therefore shows tokens and no cost.

Each chart is split so it stays under the handful of series a reader can tell apart by colour: tokens by model and tokens by type are two charts rather than one grouped by both, and the two latency percentiles are two charts rather than twelve lines on one.

Two token widgets look similar and are not. `token_count` is the raw number of tokens; `consumed_token_throughput` is weighted on the model burndown rate and is the figure quota accounting uses. They are charted separately on purpose.

There is deliberately **no "share of tokens served from cache" tile**. It could only read the partner-model cache types, which are zero unless the caller drives prompt caching explicitly, while Gemini's implicit cache reads never appear under any cache type. Such a tile reads a steady 0% precisely when caching is working hardest.

An error-rate alert firing on a Gemini pay-as-you-go model means contention on a shared resource, not an exhausted project quota. Those models have no per-project requests-per-minute limit, so there is no quota increase to request; the alert dates a degradation. Partner models do carry fixed per-region quotas, where the same signal reads differently. The `error_category` chart tells the two apart **when Vertex populates that label**, which it frequently does not on Gemini traffic; an empty chart there says nothing about the cause.

### Vertex AI: tuning the error-rate alert

The alert watches the share of invocations **of a single model** answered with a given response code, 429 by default. Two defaults carry most of the behaviour and are worth understanding before changing them.

`min_invocations` (default 20) is a floor on the denominator. A ratio over a handful of calls is arithmetic rather than signal: one failure out of two reads as 50%. Below the floor a model is not evaluated at all, so a model with little traffic is deliberately unwatched.

`window_seconds` (default 7200) is wide because of that floor. The window has to hold enough invocations to clear it often enough for the alert to see anything: narrowing it to minutes makes most windows ineligible and the alert blind, while widening it costs detection latency. On the workload these defaults were measured against, two hours kept two thirds of the windows evaluable.

`threshold_ratio` (default 0.05) sits above a measured resting rate, not at an aspirational one. **On shared Gemini capacity a low background rate of 429 is normal**, and a threshold under it alerts on healthy traffic: on one production project the busiest model sat around 2.5% at rest with day-long clusters above 5%, and a 1% threshold would have opened an incident about nine times a week with nothing wrong. Measure your own resting rate before lowering it.

Running this service costs nothing at current Cloud Monitoring prices: the Vertex AI metrics are Google Cloud system metrics, which are not chargeable to ingest, dashboards are not a billable feature, and console-issued reads are exempt from the read API price. The service creates no log-based and no custom metric. Alerting policies become billable no sooner than 2027-09-01, and not at all under a commit contract active on 2026-05-31.

### Enabling Vertex AI monitoring

`vertex_ai.enabled = true` brings up the dashboard and the error-rate alert. Each of them can be turned off on its own.

**Cost thresholds are always yours to declare.** The module ships none, so no cost alert exists until you write one. Routing is declared once on `alerts.cost` and every threshold inherits it; the chain runs threshold, then cost family, then service, then the module root. An enabled threshold that resolves to no channel at all is rejected at plan time, since it would open incidents nobody is told about; silencing one on purpose is `notification_enabled = false`. The map key is the policy identity: renaming a threshold destroys and recreates its alert policy and loses its incident history. A dollar amount is a budget, and unlike a utilisation ratio it does not transfer between projects: 60 USD a day is meaningful for one and meaningless for the next, so a shipped default would look configured without being so. Each entry becomes its own alert policy, which is how a warning and a critical raise distinguishable incidents.

```hcl
vertex_ai = {
  enabled = true

  alerts = {
    cost = {
      # Declared once, inherited by every threshold below. Prompts default to
      # opening and closing, so only the channels usually need stating.
      notification_channels = local.platform_channels

      thresholds = {
        daily_warning = {
          threshold_usd = 60
          severity      = "WARNING"
        }
        daily_critical = {
          threshold_usd = 100
          severity      = "CRITICAL"
        }
        # Overrides only what it needs; the rest stays inherited.
        hourly_spike = {
          threshold_usd         = 20
          window_seconds        = 3600
          severity              = "WARNING"
          notification_channels = local.oncall_channels
        }
        # Silenced on purpose: the policy exists, nobody is notified.
        experiment = {
          threshold_usd        = 5
          notification_enabled = false
        }
      }
    }
  }
}
```
