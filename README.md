# Terraform GCP Services Monitoring Module

This module creates a set of monitoring alerts for Google Cloud Platform services.

Supported services:

- Cloud SQL
  - CPU usage
  - Storage usage
  - Memory usage

- Memorystore
  - CPU utilization alerts for Redis instances and Redis clusters
  - Memory (system memory usage ratio) alerts for Redis instances and Redis clusters

- Kyverno
  - Error logs for admission-controller, background-controller, cleanup-controller, reports-controller

- cert-manager
  - Error logs for cert-manager controller when an Issuer or ClusterIssuer is missing

- Konnectivity agent
  - Alert when no pods are available for the konnectivity-agent deployment

- SSL certificate expiration
  - SSL certificate expiry alerts for monitored endpoints

- Typesense
  - Uptime checks for HTTP endpoints
  - Pod restart alerts for Typesense containers

- LiteLLM
  - Uptime checks for HTTP endpoints
  - Pod restart alerts for LiteLLM containers

- Vertex AI
  - Consumption dashboard: a note stating that the cost is an estimate and when the price table was last checked, estimated cost per model, tokens by model and by type, consumed token throughput, invocations per second per model, invocations by response code and by error category, invocation latency p50 and p95, first-token latency, share of prompt tokens served from cache
  - Estimated-cost alerts on one or more named thresholds, each with its own window and notification channels
  - Invocation error-rate alert on the share of a given response code, 429 by default

### Vertex AI: the price table is yours to maintain

**Read this before enabling the service.**

Vertex AI publishes token counts to Cloud Monitoring but **no spend metric**, so this module cannot read your cost from Google. It estimates it: tokens multiplied by the published list price, in USD. The price table ships as a module default in `vertex_ai.pricing` and **must be reviewed and updated periodically**.

There is no way to automate that review. Google publishes no price API covering every model: partner models have no SKU in the Cloud Billing Catalog, and the embedding SKU cannot be identified from it. So the table is hand-written, and it rots silently. A stale price produces a confident wrong number with no error, no warning and no visible symptom.

Three ways it goes stale, all seen in practice:

- **A price changes.** Introductory pricing is the common case; one entry in the shipped table expires on 2026-12-31 and doubles the day after. Each such entry carries a comment naming the date.
- **A new model appears.** A model routed through your gateway shows up in the token widgets immediately and contributes nothing to the cost, because it has no price. Comparing "Tokens by model" against "Estimated cost by model" is how you spot it: a model present in the first and absent from the second has no price.
- **Your own table drifts from the module's.** If you override `pricing`, you own it entirely, including `pricing_verified_on`, the date the dashboard shows.

Put this on a recurring issue. Re-run an inventory of the live `token_count` series before each review, so models that appeared in the meantime are caught rather than assumed absent.

### Reading the Vertex AI dashboard

The dashboard states in its first tile that the figures are an estimate and when the table was last checked. The estimate is not what you are invoiced: list prices ignore committed-use discounts, negotiated rates and credits. The authoritative figure is the BigQuery billing export, which is SKU-level and lags by about a day.

Each chart is split so it stays under the handful of series a reader can tell apart by colour: tokens by model and tokens by type are two charts rather than one grouped by both, and the two latency percentiles are two charts rather than twelve lines on one.

Two token widgets look similar and are not. `token_count` is the raw number of tokens; `consumed_token_throughput` is weighted on the model burndown rate and is the figure quota accounting uses. They are charted separately on purpose.

The cache token types (`cache_read_input`, `cache_write_input`, `cache_write_1h_input`) are observed on partner-model series but are **not documented**: the metric descriptor only defines `input` and `output`. Validate them against a real request before treating the cache part of the estimate as reliable.

An error-rate alert firing on a Gemini pay-as-you-go model means contention on a shared resource, not an exhausted project quota. Those models have no per-project requests-per-minute limit, so there is no quota increase to request; the alert dates a degradation. Partner models do carry fixed per-region quotas, where the same signal reads differently. The `error_category` chart separates the two cases.

Running this service costs nothing at current Cloud Monitoring prices: the Vertex AI metrics are Google Cloud system metrics, which are not chargeable to ingest, dashboards are not a billable feature, and console-issued reads are exempt from the read API price. The service creates no log-based and no custom metric. Alerting policies become billable no sooner than 2027-09-01, and not at all under a commit contract active on 2026-05-31.

### Enabling Vertex AI monitoring

`vertex_ai.enabled = true` brings up the dashboard and the error-rate alert. Each of them can be turned off on its own.

**Cost thresholds are always yours to declare.** The module ships none, so no cost alert exists until you write one. A dollar amount is a budget, and unlike a utilisation ratio it does not transfer between projects: 60 USD a day is meaningful for one and meaningless for the next, so a shipped default would look configured without being so. Each entry becomes its own alert policy, which is how a warning and a critical raise distinguishable incidents.

```hcl
vertex_ai = {
  enabled = true

  alerts = {
    cost = {
      thresholds = {
        daily_warning = {
          threshold_usd = 60
          severity      = "WARNING"
        }
        daily_critical = {
          threshold_usd        = 100
          severity             = "CRITICAL"
          notification_prompts = ["OPENED", "CLOSED"]
        }
        # Silence one without deleting it.
        hourly_spike = {
          threshold_usd  = 20
          window_seconds = 3600
          enabled        = false
        }
      }
    }
  }
}
```
